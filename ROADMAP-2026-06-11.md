**Date:** Thursday, June 11, 2026
**Goal:** Implement & test everything outstanding, then publish/ship.

## Architecture: local pre-filter → AI → local parse

Every AI-touching feature follows the same shape: **filter/prepare locally first, call the AI, then parse/validate the AI output locally** before acting.

- **Review flow:** `filterDiff` strips lock/min/map files and caps the diff at ~80k chars; `getOpenIssueSummary` / `getMergeFollowUpItems` parse prior reviews with regex (all local) → **then** `reviewDiff` / `summarizePR` call the AI.
- **Requirements → issues + spec:** detect the trigger and read `requirements.md` (local) → `generateSpecAndIssues` calls the AI → `parseSpecResponse` + YAML validation parse the result (local) → issues created.
- **AI provider:** `providers.js` defaults to **`anthropic` (Claude API)**. Set `AI_PROVIDER=anthropic` + `ANTHROPIC_API_KEY` and everything routes through Claude. OpenAI/Gemini remain available as drop-in alternatives but are not required.

## 0. Where the code stands today

A GitHub App webhook server (Express) that auto-reviews PRs through a pluggable AI provider.

| File | Responsibility |
|------|----------------|
| `index.js` | Express server, single `/webhook` route, signature verification, event routing (`opened` / `synchronize` / merge-close). |
| `githubService.js` | All Octokit calls: diff fetch + filter, linked-issue lookup, prior-review parsing, merge follow-up extraction, `createFollowUpIssue`, `postReviewComment`. |
| `aiService.js` | `reviewDiff` (review prompt) and `summarizePR` (retrospective). Prompt engineering lives here. |
| `providers.js` | `getProvider()` abstraction over Anthropic / OpenAI / Gemini, switched by `AI_PROVIDER`. |
| `package.json` | Deps present; **only script is `start`** — no `test`, `lint`, or `dev`. |

**Already working:** PR-open/synchronize review, cross-round open-issue tracking, merge-commit "not ready" warning, merge retrospective + follow-up issue creation, 3-provider switching.

**What's missing for a real ship (the gaps this roadmap closes):**

1. The 3 items already in `TODO.md` (follow-up template + 403 fix, requirements→issues/spec, debug-log cleanup).
2. **No tests at all** — nothing protects the regex-heavy parsing in `githubService.js` / `aiService.js`.
3. **No README** and **no `.env.example`** — nobody can deploy this without reading source.
4. **No `issue_comment` webhook** — required for the `/leadbot` slash command.
5. **No health check, no startup env validation, no graceful failure** if `PRIVATE_KEY_PATH` is missing.
6. **No Dockerfile / CI** — required to actually publish.

### Phase 3 — Fix follow-up issue template + 403

TODO item #1. Two sub-problems: the template quality and the permission error.

**3a. Investigate the 403 "Resource not accessible by integration"**
- [ ] This is almost always a **GitHub App permissions** issue, not a code bug. The `Issues: Read & Write` permission must be granted **and the installation re-authorized** — GitHub does not retroactively apply new permissions to existing installations; the user must approve the permission request in their org/repo settings.
- [ ] Confirm the App manifest/settings request `Issues: write` and `Pull requests: write`. Re-accept the permissions on the test repo's installation.
- [ ] Add a friendlier catch in `createFollowUpIssue` (or its call site in `index.js`) that detects `err.status === 403` and logs an actionable message ("re-authorize the App's Issues permission") rather than a raw stack.

**3b. Redesign `createFollowUpIssue()` body in `githubService.js`**
- [ ] Replace the current flat list with a structured, actionable template:
  - Header line linking back to the PR (`#${pullNumber}`).
  - Collapsed `<details>` "Context" section.
  - **Checkbox** task lists (`- [ ] ...`) instead of plain bullets, so the items are trackable in GitHub's UI.
  - Group by severity with clear `##` sections (Critical/High, TODOs Before Merge, Medium/Low).
  - Footer noting it was auto-generated.
- [ ] Keep the `ensureLabel` + `technical-debt` label logic; consider also adding a `severity:high` label when blockers exist.

**Verify:** Unit-test the new body builder (extract it as a pure `buildFollowUpBody({todos, mediums, blockers, pullNumber})` function). Assert checkboxes render and the PR back-link is present. Manually trigger a merge on a test PR with known issues and eyeball the created issue.

### Phase 6 — Hardening & correctness pass

Catch the things that'll bite in production.

- [ ] **Private key read on every call:** `getOctokit` does `fs.readFileSync(PRIVATE_KEY_PATH)` on every single Octokit instantiation. Read it once at module load (or memoize). Minor, but it's a needless sync disk read per API call.
- [ ] **Webhook idempotency:** GitHub retries deliveries. `synchronize` can fire rapidly. Confirm the merge-commit branch and auto-spec path won't double-post. Add a simple in-memory de-dupe on `delivery id` (header `x-github-delivery`) if needed.
- [ ] **`res.status(200).send('Processing')` then async work:** if the async work throws after the response is sent, it's only caught by the top-level try/catch (good) — confirm nothing can throw *before* that catch is set up.
- [ ] **Diff truncation at 80k chars** may cut a file mid-hunk; acceptable for today, note it as a known limitation in the README.
- [ ] Confirm `botMatchesLogin` normalization still matches your actual App slug (`GITHUB_APP_SLUG`).

**Verify:** `npm test` green; restart server and re-run the manual PR flow once end-to-end.

### Phase 7 — Test suite

This is the "test what is missing" half of the request. Target the pure, regex-heavy logic — highest bug-risk, easiest to cover.

Create `*.test.js` files (vitest). Priority order:

- [ ] `parsers.test.js` (or against the extracted functions):
  - `filterDiff` — drops lock/min/map files, caps at 80k, keeps real source.
  - `botMatchesLogin` — `myapp[bot]` / `myapp` / `myapp-bot` all match.
  - `isRetrospectiveComment` — matches the three retro/merge headers, rejects normal reviews.
  - Merge follow-up regexes — extract `[TODO before merge]`, `[Medium]/[Low]`, `[Critical]/[High]` across bold/italic markdown variants; de-dupe.
  - `getOpenIssueSummary` open-vs-addressed split given a touched-files set.
- [ ] `aiService.test.js`:
  - `buildPRStats` — rounds, resolved-between-rounds, persistent issues.
  - `parseSpecResponse` — happy path, missing YAML block, extra prose (from Phase 4).
- [ ] `githubService.test.js` — mock Octokit (vitest `vi.mock`): `createIssuesFromSpec` calls, `createFollowUpIssue` body shape, 403 handling.
- [ ] One **integration-ish** test of `index.js` routing: feed a fake `opened` payload to the handler (export the handler or use `supertest` against the Express app) and assert the right service functions are invoked. `npm i -D supertest`.

**Target:** all green, meaningful coverage of the parsing layer (the part most likely to silently break).
